# DeepCover 性能基准结果

本文记录一次可复现的本机基准实验。它用于量化当前实现的开销范围，不代表生产环境容量承诺。

## 测试方法

- 日期：2026-09-20
- 操作系统：Windows 10.0.19045
- CPU：Intel Core i5-10210U，4 核 8 逻辑处理器
- 内存：23.8 GB
- Java：Oracle JDK 1.8.0_202
- Git 基线：`c9cc66e822ea72a239e052acee32b9c8051d6d6f`；运行时工作区包含本文对应的未提交改动
- 应用：仓库内 `examples/demo-servlet`，嵌入式 Jetty
- 发送端：HTTP 模式；接收端为同机 Python HTTP Server
- 负载：50、100、200 目标 RPS；并发上限 64；每轮预热 200 请求；每个负载持续 15 秒
- 重复次数：每个负载和采样组合运行 3 次，表格使用中位数并保留范围
- Baseline：仅运行 demo，不加载 JVM Sandbox 或 DeepCover
- 10% / 100%：加载 JVM Sandbox 和 DeepCover，分别配置 `sampleRate=1000` 和 `sampleRate=10000`

执行命令：

```powershell
.\benchmarks\run-benchmark.ps1 `
  -TargetRps '50,100,200' `
  -DurationSeconds 15 `
  -Concurrency 64 `
  -Warmup 200 `
  -Repeats 3 `
  -DrainTimeoutSeconds 120
```

结果汇总命令：

```bash
python benchmarks/summarize_results.py benchmarks/results/<timestamp>
```

## 采样与发送校验

| 场景 | 已采集 / 总请求 | 实际采集比例 | 发送失败 |
|---|---:|---:|---:|
| 10% 采样 | 1540 / 17563 | 8.77% | 0 |
| 100% 采样 | 17567 / 17567 | 100.00% | 0 |

18 个 Agent 运行场景均满足：队列最终深度为 0、`sendFailed=0`，接收端请求数与 `sendSuccess` 完全一致。10% 场景采用确定性 traceId 哈希；在这组有限且多轮复用的 trace 集合上，实际命中率是 8.77%，不应被理解为随机采样器的统计置信区间。

## 结论边界

1. 在 50 和 100 RPS 下，三组都能维持目标吞吐，但 DeepCover 增加了明显的 CPU、常驻内存和尾延迟成本。
2. 200 RPS 已接近或进入该 demo 在本机上的饱和区。此时 10% 和 100% 采样都降低了实际吞吐，中位吞吐分别下降约 8.7% 和 19.0%，P99 中位数均超过 1.1 秒。
3. 10% 采样并不等于 10% 的总开销。Servlet 入口判断、Sandbox 事件分发、类增强和固定运行时资源仍然存在。
4. Baseline 未加载 Sandbox，因此表中增量是“Sandbox + DeepCover”的整体部署成本，不是对 DeepCover 模块自身的隔离测量。
5. 三轮 P99 波动较大，尤其是 200 RPS 基线。本结果可用于识别成本量级和趋势，不能据此声明生产容量上限。
6. 接收端与应用位于同一台机器，没有覆盖真实网络、远程 Kafka、容器资源限制、GC 日志分析、长时间稳定性或复杂业务调用栈。

生产使用前，应在目标服务、目标 JDK、真实流量模型和资源限制下重新执行，并将 P99、CPU、RSS、队列深度和发送失败率纳入准入标准。
